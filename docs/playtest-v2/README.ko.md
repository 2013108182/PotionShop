## 설계 판단

주민 다이어리는 채택할 가치가 있다. 현재는 주문 대사가 날짜에 붙어 있고 성공 이력이 없어서, 도움의 의미와 인물의 변화가 다음 방문에 안정적으로 남지 않는다. 기록을 남기는 시스템은 F05의 반복 감사, F06의 다음 목표, F03의 방문 예고를 함께 뒷받침한다. 다만 숫자 호감도를 올리는 일이 목적이 되면 반복 주문 노동만 늘 수 있으므로 **새 정보·개인의뢰·그 이후의 생활 변화**를 핵심 보상으로 둔다.

친밀도만으로 모든 이야기를 자동 해금하지 않는다. 응대 이력은 관계의 바탕이며, 각 주민의 이야기 사건을 실제로 만나고 해결해야 다음 장으로 이동한다. 세이브 불러오기·창 반복 열기·같은 날 반복 질문은 진전을 만들지 않는다. 품절이나 거절 한 번으로 관계를 깨거나 개인 이야기를 영구 실패시키지 않는다. 금액 많이 쓰기/싼 물약 반복 구매/선물 연타가 최적 진행법이 되지 않게 한다.

## 권장 후속 구현 순서

0. 기존 F08/F09 실행 검증 차단 해소 후 회귀 테스트/전체 분석. 이 단계는 아직 완료되지 않았다.
1. 콘텐츠ID·튜토리얼 상태 계약을 확정하고 안정된 주민/주문/방문 ID, 버전 있는 저장 이행과 멱등 사건 기반을 마련. 기존 두 물약·day1–3 진행부터 회귀 검증.
2. React guided 튜토리얼을 현재 첫 로빈 주문에 대응하고 중간저장·기존세이브 면제를 검증. 이후 엘리의 밤 시야 연구는 자유 연구로 유지. 목표별 연구 세션은 새 물약1종부터 연결.
3. 로빈·엘리부터 호감도·다이어리 정보1–2단계·개인의뢰·후기 한 사이클을 연결. 호감도만 높으면 자동완료되는 구조인지, 실패·재접속 중복보상이 생기는지 검사.
4. 콘텐츠 표의 우선 레시피와 나머지 기존 주민을 추가. 새로운 주민/정보/의뢰가 한 방문에 과도하게 몰리지 않는지 작은 플레이테스트로 확인.
5. 희귀 해금 이후 주민/레시피/방문 예약 데이터 확대. 실제 미래 방문을 수요 예고에 연결하고 F10 원장·F07 투자정보와 통합.
6. 나머지 개인 이야기와 카탈로그를 확장. 실제 방문수/새정보 빈도/미완료 의뢰 적체/반복감으로 제안 수치를 조정. 마지막에 아트.

## 검증과 전달 상태

이번 확장은 기존 React 및 Flutter 소스 독해와 담당 간 설계 검토다. 신규 시스템 코드는 구현하지 않았고 테스트를 실행하지 않았다. 기존 Flutter/Dart SDK의 공식 artifact 다운로드 CONNECT403 차단 상태와 v1 QA 기록을 그대로 유지하며 추가 우회 시도는 하지 않는다.

Library 업로드 재시도 없음. 부모 스레드에 한국어 기획 본문과 로컬 문서를 전달하며 첨부 제작은 부모가 수행한다. 과거 첫 세 날 보고서는 신규 다이어리나 이후 콘텐츠의 플레이 검증 자료가 아니다.
