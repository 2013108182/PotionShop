## SR01 — 답 순서를 전달하지 않는 첫 연구 (CR01/F01)

**현재 문제.** `_beats` 연구 메모가 정답 세 재료를 정답 순서로 소개하면서 hint는 “순서는 실험 기록으로 찾기”라고 한다. `ResearchStudio.shelf`는 여섯 기본 재료를 글로벌 `ingredients` 배열 순서로 보여준다. 성질의 방향은 일치하므로 재료 이름이나 효능을 바꾸지 않는다.

**제안.** 메모에서는 요구 효능인 빛·감각을 안내하고 정답 세 재료의 이름을 열거하지 않는다. 콘텐츠의 여섯 재료 고정 배열 `mushroom, web, petal, moon, tear, salt`를 선반에 사용한다. 어떤 화면 폭에서도 정답 세 재료가 정답 순서로 연속하지 않도록 읽기 순서와 접근성 순서를 검증한다. 슬롯은 빈 상태로 시작하며 초기 inspected 재료도 없음으로 바꿔 `moon`을 답처럼 강조하지 않는다. 선택·제출은 자유다. 선반 배열은 별도 `researchIngredientDisplayOrder`로 관리하여 레시피 배열을 UI 정렬에 재사용하지 않는다. 재료 성질은 유지하고 콘텐츠의 자발적 도움 세 항목은 실패 횟수·돈·재료와 무관하게 열 수 있게 한다.

**상태/이벤트.** 텍스트·표시 순서만 바꾸면 저장 스키마 변경 없음. 연구 답·기록·보상은 그대로. `recipeDiscovered(sight)`는 기존처럼 처음 발견 시 실험 물약 1병만 지급한다. 이미 풀었거나 미완성 노트로 진입하면 슬롯/시도 기록을 재배열하지 않는다.

**수용 기준.** 첫 화면의 후보 설명에 정답 3개가 정답 순서로 연결되어 있지 않음; 후보 클릭 순서를 강요하지 않음; 첫 제출 정답이면 바로 발견/1병; 오답은 0G·재료0 소모; 기존 노트 복원과 독립 연구→상점 이관에서 중복 보상 없음. `opening_test.dart`, `research_test.dart`, `game_reveal_test.dart`에 해당 흐름 회귀 기준을 둔다.

## SR02 — 연구별 수동 주석 (CR02/F02)

**현재.** `ResearchSession`은 `slots`, `activeSlot`, `attempts`만 저장한다. 과거 조합 재사용과 집계 점수는 있으나 제외·가설 메모가 없다.

**제안 데이터/API.** 노트에 `researchId: sight`, `marks: Map<ingredientId, candidate|hold|excluded>`, `memo: String` 추가. 키 부재는 미표시. `setMark(id, mark?)`, `setMemo(text)`로 변경하고 UI에 “내 가설”로 표시한다. 메모는 200자 상한, 새 줄 허용, 개인정보 입력 요구 없음. 재료 표시는 텍스트/기호를 같이 제공하여 색만으로 구별하지 않는다. 재료 버튼과 표식 버튼은 구분해 표식 변경이 슬롯에 재료를 넣지 않게 한다.

**규칙.** 점수와 주석은 독립이다. 오답 0개 결과를 보고 자동으로 제외하지 않으며, 정답 여부를 암시하지 않는다. 제외 표시 재료도 클릭·드래그 후 “제외 표시한 재료예요. 다시 시험해 볼까요?”의 `넣기 / 돌아가기`로 투입 가능하다. 확인은 플레이어 표시 재료에만 적용하며 정답 여부를 읽지 않는다. 시도 재사용은 슬롯만 바꾸고 주석을 지우지 않는다. `슬롯 비우기`는 확인 없이 세 슬롯만 비우며 기록·표식·메모를 보존한다. `내 메모 지우기`만 별도 확인 후 표식·메모를 비운다. 기존 연습용 `새 노트`는 조합·실험 기록을 새로 시작하되 표식·메모는 복사해 유지하며, 상점 발견 레시피/재고도 보존한다. 기존 연습노트 파괴 확인과 새 메모 삭제 확인을 하나로 합치지 않는다.

**저장.** ResearchSession version 2를 새로 쓰고 1/2를 읽는다. v1은 `researchId=sight`, 빈 marks/memo로 이행. Game 노트 문자열과 독립 연구 키 모두 같은 디코더를 사용한다. 기존 SharedPreferences 키는 유지해 이어하기가 끊기지 않게 한다. 알 수 없는 연구/재료/mark 값은 검증하고 손상 주석은 빈값으로 복구할 수 있지만 검증된 슬롯·점수 기록은 유지한다. 악성/잘못된 핵심 시도 기록 검증은 완화하지 않는다.

**수용 기준.** 0완벽/0불안정 제출이 자동 주석을 만들지 않음; 제외 재료로 정답 제출 가능; 200자 경계와 한글 입력; 상점·독립 연구 재진입/앱 재시작 후 복원; v1 fixture 복원; 슬롯 비우기로 메모 유지, 메모 삭제 취소/확인, 새 노트에도 메모 유지; 360×800에서 메모가 제출 버튼을 가리지 않음.

## SR03 — 밤 준비에 사용할 다음날 수요 (CR03/F03)

**현재.** `prepare/buy/brew`는 낮에도 가능하고 `orders`는 현재 `day`에 종속된다. `nextDay`는 현재 일일 수치를 초기화한다. 알려진 수요를 미리 보여주는 순수 조회가 없다.

**최소안.** `ordersForDay(day, completed)`를 순수 함수로 추출하고 현재 `orders`도 동일 함수를 사용한다. `previewNextDay()`는 게임의 날짜·고객 위치·돈·재고를 변경하지 않고 내일 주문을 조회한다. UI에는 “내일 방문 예정”, 물약별 요청량, 현재 재고, 추가 준비량 `max(0, 요청량−재고)`를 표시한다. night1은 엘리 시야1/로빈 숙면1/준 시야1, 합계 시야2·숙면1. 연구 성공 직후 실험 시야1병이 있으므로 시야 추가 준비량1병이다.

**협회 분리.** day2 밤부터 day3 협회 시야3병을 “기한 없는 별도 주문”으로 표시할 수 있으나 내일 개인 수요와 자동 합산/재고 차감하지 않는다. 플레이어가 “협회 몫 포함”을 선택할 경우 별도 표시된 목표량에만 더한다. 아직 발견하지 않은 물약은 “연구 후 준비 가능”이며 구매·제조 버튼을 잠그고 연구로 안내한다. 이미 협회 납품을 마쳤으면 해당 미납 목표는 0이다.

**이점.** 주문을 기다리는 동안 제조 화면을 다시 열지 않아도 되는 실제 행동 감소를 안내한다. 사전 준비를 권하되 준비하지 않았다고 벌점·품절 확정·가격 할증을 부과하지 않는다. “예약”이라는 단어는 확정 예약 상태/취소 처리가 생기기 전에는 쓰지 않는다. 정확한 배열 기반 예고이며 통계 예측으로 포장하지 않는다.

**저장/테스트.** 조회 결과는 저장하지 않아 재고·납품 변경 후 즉시 재계산한다. 별도 포함 체크는 화면 상태만 둔다. `ordersForDay(1/2/3/4, completed)`가 기존 주문과 같고 미리보기 전후 `Game.encode()`가 동일해야 한다. 시작 재고·0재고·초과재고·미발견·납품 전후의 부족량 검증. 추가 준비량은 수요량이며 가마솥 생산은 아래 SR07 배치 규칙 때문에 초과될 수 있음을 표시한다.

**보류안.** 예약금, 준비 보너스, 기다림 제한, 동적 수요, 낮 제조 금지는 별도 경제·사용성 검증과 신규 기능 승인 전 구현하지 않는다.

## SR04 — 선택이 없는 거래의 조작 축소 (CR04/F04)

**현재.** `PotionSelection`은 항상 선택 전 상태부터 시작한다. 사용자 “대화→고르기→한 종류 선택→건네기” 흐름이며 `onGive` 이후 선택을 비운다. 도입부도 같은 컴포넌트를 사용하지만 stage 진행과 일반 상점 판매 호출이 다르다.

**제안 조건.** 알려진 전체 레시피가 정확히 1종이고 해당 재고>0, `enabled=true`, 첫 판매 안내 완료 상태이면 “숙면 물약 건네기 · 35 G” 단일 수동 버튼을 제공한다. 후보가 여러 개인데 재고가 한 종만 남았다는 이유로 자동 추천하지 않는다. 요청 정답ID를 보고 후보를 좁히지도 않는다. 여러 알려진 물약은 기존 선택 UI 유지. 첫 안내 완료 여부는 성공 이벤트 기반이며 도입부 실패/건너뛰기를 완료로 오인하지 않는다.

**호출 계약.** 직접 버튼도 기존 `onGive(id)` 한 번만 호출한다. UI에서 돈·재고를 직접 바꾸지 않는다. 고객 미도착/응답 중/재고0이면 비활성, 연속 탭은 같은 방문 token으로 차단한다. 다음 손님 도착 전 자동판매하지 않는다. 현재 잘못된 제안 1회 설명과 2회 이탈 규칙을 유지한다.

**저장/경계.** 학습 완료 flag는 SR05의 성공 이력 또는 독립 `serviceTutorialDone` 중 하나를 채택해 중복 상태를 만들지 않는다. 기존 저장은 이미 `served>0`인 현재 날 또는 도입부 stage를 통해 확인 가능한 경우에만 추론하고, 증거가 없으면 안내 1회가 다시 나오는 쪽을 택한다.

**수용 기준.** 첫 거래는 안내 유지, 다음 동일 단일종 거래는 종류 선택 한 단계 감소; 다종·품절·미도착·다음 손님 전환은 기존 경계 유지; 더블탭에서 1병/35G만 처리; 도입부와 자유 상점 모두 검증. `service_sequence_test.dart`, `service_penalty_test.dart`, `opening_test.dart` 확장 대상.

## SR05 — 고객 반응과 로빈의 약속 회수 (CR05/F05)

**현재.** 도입부 stage2 로빈이 재료를 가져오겠다고 약속한다. 일반 상점 `controls`의 판매 성공 반응은 공통 문장이다. `CustomerOrder`에 고객ID가 없으며 약속·방문 성공 이력·보상 수령 상태도 없다. 새로운 지급 이벤트는 누락된 구현을 임의 추정해 즉시 더하는 대상이 아니라, 콘텐츠와 수량을 확정해 승인받을 설계다.

**데이터.** `CustomerOrder`를 필드명 있는 `OrderDefinition(id, customerId, text, potionId)`로 바꾸거나 호환 어댑터를 둔다. ID는 `robin/mina/ellie/jun`으로 고정하고 이름/번역문으로 판정하지 않는다. 방문ID는 `day:orderIndex:customerId`. 영속 상태는 `successfulCustomerVisits`, `robinPromise: unknown|promised|fulfilled`, `claimedEventIds`로 둔다. 무제한 방문 로그 대신 대사에 필요한 횟수·최근 성공 물약과 1회 이벤트만 저장한다.

**전이.** 도입부 첫 로빈 거래 성공 후 실제 약속 대사가 나오는 전이에 `promised` 기록. 이후 로빈 방문 도착 시 `promised`이고 미수령이면 `robin_material_thanks_01` 처리: 거미줄1+정령의 눈물1을 창고에 추가하고 같은 스냅샷에 `fulfilled`/claim 기록. 당일 물약 구매 성공을 선물 조건으로 삼지 않아 과거 약속을 추가 구매와 교환하지 않는다. 반응문에는 선물 종류·수량과 지난 숙면 도움을 표시한다. 첫 호출 이후 창 열기·닫기·저장 재시도·도입부→상점 이관으로 재지급하지 않는다.

**권고 API.** `onVisitArrived(visitId)`는 새 이벤트 결과 또는 없음 반환; `sell` 성공은 `SaleOutcome`에 customerId/visitId/potionId 포함; `reactionFor(outcome, history)`는 콘텐츠 표의 안정된 키로 대사를 선택. 애니메이션 rebuild에서 지급하지 않는다. Game 변이와 claim을 먼저 한 덩어리로 만들고 기존 저장 큐를 통과시킨다. 저장 실패 상태를 알리고 다시 온 것이 확인되지 않은 저장에 대해 수령 완료를 보장한다고 말하지 않는다.

**구버전.** 과거 판매 누적을 현 `served`로 역산하지 않는다. 기존 Game은 `unknown`으로 이행하며 소급 선물 지급 금지. 도입부 저장이 약속 이후이고 다음 로빈 방문 전임을 stage+day로 확정할 수 있는 제한된 fixture만 `promised`로 이행할 수 있다. 그 외에는 후속 콘텐츠가 명시적으로 새 약속을 설정하기 전까지 미확인 상태 유지. `storySaveKey`와 자유 상점 저장을 서로 합치지 않는다.

**수용 기준.** 약속 대사 노출→다음 방문→재료 각1 추가→재진입/재시작 추가0; 이전 선물이 오늘 판매를 거절해도 유지; 최초/재방문/미구매 반응이 잘못 섞이지 않음; 이름 바뀌어도 ID 로직 동일; 구세이브에 대량 소급 지급 없음. 새 재료 선물은 현금 매출에 합산하지 않으며 SR08 비현금 보상 항목에 기록한다.

## SR06 — 희귀 거래 해금 후 정직한 목표 안내 (CR06/F06)

**현재.** `deliver`가 120G와 `supplierUnlocked=true`를 부여한다. `objective`는 해금 완료 문구를 계속 사용하고, `guildOrder`는 희귀 상인 버튼을 제공한다. 현 코드의 두 레시피는 root/fairy를 사용하지 않는다. 숨겨진 다음 연구가 있다는 문구는 근거가 없다.

**최소안.** 납품 완료/재료 상세에서 “현재 이야기의 특별 주문을 마쳤어요. 기존 물약 영업은 계속할 수 있어요. 희귀 재료를 쓰는 연구는 현재 준비되어 있지 않아요.”처럼 현재 범위를 명시한다. 다음 행동은 기존 영업·제조·이미 존재하는 장부로만 안내한다. 가격이나 거래 자체를 바꾸지 않되, 희귀 재료 구매 전에 현재 레시피 사용처가 없음을 읽을 수 있어야 한다. 저장 변경 없음.

**후속 보류.** 희귀 물약 추가에는 effect/재료성질 검토, `Potion` 카탈로그, 연구 targetId, 연구별 노트, 발견 조건, 새 요청·후기·소개·협회 연결, 경제 검증이 필요하다. 현 `potions[1]`/`sight` 하드코딩을 제거하는 별도 명세와 승인 없이는 CR06의 새 부탁 초안을 구현하지 않는다.

**수용 기준.** 납품 전 목표 유지; 완료 직후 현재 행동과 콘텐츠 경계 확인 가능; 지원하지 않는 연구 버튼/도착일/효능 약속 없음; 납품 반복 보상 불가, 기존 영업 지속. 아트 자산 없이 텍스트/현재 패널만 사용한다.

## SR07 — 배치 원가와 투자 판단 정보 (CR07/F07)

**현재.** 레시피 한 세트 재료가 각2G×3=6G이며 `setsFor(quantity)=ceil(quantity/level)`이다. `prepare`는 부족한 재료만 현금 구매하고 `sets*level`병을 생산한다. `equipment`는 이미 6G/세트·현재 병당 `6/level`G를 표시한다. 추가가 필요한 것은 다음 단계 비교·조건 있는 회수량·수요 연결이다.

**조회 모델.** `CraftQuote(potionId, requested, batchCount, produced, materialUnits, replacementCost, cashShortageCost)`를 순수 계산으로 만들고 제조와 비교 UI가 이를 공유하도록 계획한다. `replacementCost=sum(재료시가)*batchCount`; `cashShortageCost`는 현재 `prepareCost`와 같음. 재료가 창고에 있다고 원가를 0G로 표현하지 않는다. 미래 레시피 원가도 하드코딩6이 아니라 recipe/ingredients 가격 합으로 계산한다.

**표시.** Lv1→2는 투자90G, 한 세트1→2병, 전량 활용 기준 평균6→3G/병. “재료 절감액 기준 약30병 (90÷3), 실제 현금 회수 기간 아님”으로 표기. 정확한 주문수량 비교는 `6*ceil(q/1)-6*ceil(q/2)`를 사용한다. 3병 목표는 Lv2에서4병을 생산하므로 남은1병까지 소비될 때의 평균과 목표3병에 즉시 배분하는 비용이 다르다. 다음날 예정 판매량/현재 재고/기한 없는 협회 잔량은 SR03 조회로 별도 표시하며 판매 완료를 보장하지 않는다.

**경계.** Lv3에서 업그레이드 없음; Lv2→3은 비용180G, 평균3→2G 차이이므로 Lv1→2의30병을 재사용하지 않는다. 알려진 레시피가 늘면 선택 레시피 기준임을 표시. 투자금 부족이면 비교는 볼 수 있고 실행만 비활성. 모델의 유효수량 1..30과 UI 배치수 1..10을 혼동하지 않는다.

**수용 기준.** q=1/2/3/30, level=1/2/3, 전량재고/일부부족/전량부족의 생산량·재료소모·현금부족분 일치; 90÷(6−3)=30 검증; 예상 수요와 실제 현금 수입 구분; `management_loop_test.dart`의 배치 초과생산·원자적 구매 실패 보존. 가격 인하·방문객 추가·투자 강요는 보류한다.

## SR08 — 거래와 놓친 요청의 의미를 보존하는 정산 (F10)

**조사 당시 문제.** `sell`과 `deliver`가 둘 다 `revenue`를 더한다. 장부는 재료 지출과 투자 필드를 이미 분리하지만 매출228G만으로 개인판매108G/협회보상120G를 구분할 수 없다. `lostSales`는 오판매 두 번 이탈만 세고 `skipCustomer`는 이유를 남기지 않는다. 재고0 판매 버튼은 비활성이고 낮 즉시 제조가 가능하므로, 품절 화면을 보았다는 사실만으로 확정 손실을 더하면 중복·허위 집계가 된다.

**결정.** F10은 신규 원장 기능으로 분류하여 이번 실행에서는 구현하지 않는다. 조사 당시 `spending`과 `investment` 및 장부 표시는 이미 분리되어 있다. 후속 구현의 핵심은 개인판매/협회보상 분리와 미구매 이유 기록, 두 정산 화면의 일관성이다. UI 표기는 “재료 구매 지출”이다. 창고 소비량의 원가와 현금 지출은 서로 다르다.

**확정 사건.** 성공 판매/납품/구매/투자 이후에만 해당 금액을 누적한다. 실패 API/단순 창 열기는 기록하지 않는다. 주문 종료 때 다음 중 정확히 하나를 붙인다: `wrongPotion` (두 번째 오제안으로 이탈), `outOfStock` (알려진 요청 물약 재고0 상태에서 주문을 받지 않기로 확정), `declined` (재고가 있어도 명시 거절), `researchPending` (미발견 물약 부탁을 기록하고 추후로 넘김). 초기 엘리의 연구 부탁은 벌점처럼 표현하지 말고 “연구 대기 1건”으로 따로 보여준다. 첫 오제안·재고0 조회 후 보충 판매는 놓친 주문0건이다. 미구매 총수에 연구 대기를 포함할지 장부 표제에 명시하고 두 수치를 혼용하지 않는다.

**구체적 최소 상태.** Game에 `salesRevenue`, `guildRewards`, `unclassifiedRevenue`(모두 정수G), `missedOrders: Map<reason,int>`, `researchPendingOrders: int`, `receivedMaterials: Map<ingredientId,int>`를 추가한다. `reason`은 `wrongPotion|outOfStock|declined|unknown` 네 값이며 연구 대기는 별도 합계다. 기존 `revenue`는 `salesRevenue+guildRewards+unclassifiedRevenue`를 반환하는 호환 getter로, `lostSales`는 missedOrders 합계 getter로 바꾼다. `DaySummary`는 이 값들과 기존 `spending/investment/served`를 읽는 불변 조회 모델이다. 추가 이력 화면이 필요하지 않으므로 지금은 전체 이벤트 로그를 저장하지 않는다.

**갱신 지점.** `sell` 성공은 `salesRevenue`만 증가; 두 번째 잘못된 물약으로 `_advance`하기 직전에 `wrongPotion` 증가. `deliver` 성공은 `guildRewards` 증가, 두 번째 납품은 불변. `skipCustomer`는 `_advance` 전 현재 요청의 `knows/stock`을 검사해 연구대기→품절→명시거절 우선순위로 정확히 한 번 분류한다. 이후 customer가 바뀌므로 같은 방문의 종료를 다시 기록하지 않는다. `buy/prepare/upgrade`는 기존 지출·투자 갱신 그대로. SR05 선물 이벤트를 수령할 때만 `receivedMaterials` 증가; SR05가 아직 구현되지 않으면 빈값. `nextDay`는 모든 신규 일일 필드와 기존 일일 필드를 함께 초기화한다. 선물 수령 claim 같은 영속 상태는 초기화하지 않는다.

**정산 조회.** 장부·마감은 동일 `DaySummary`를 사용한다. 금액은 정수G; 선물 재료는 비현금 목록으로 표시하고 현금 매출/지출에서 제외한다. 기간은 현재 `nextDay` 초기화 정책과 일치하도록 “해당 영업일 시작부터 다음날 시작 전까지(밤 준비 포함)”로 정의한다. 영업 마감 시점에 고정된 수치와 밤 구매 뒤 변하는 수치를 같은 고정 결산처럼 보여주지 않는다. 품목별 상세 조회가 필요해지면 그때 `DayTransaction`과 `OrderResolution`을 추가하는 별도 작업을 연다.

**저장 이행.** Game version 3을 쓰고 2/3을 읽는다(실제 구현 시 먼저 배포된 스키마 확장이 있으면 버전을 다시 조정). v2의 `revenue`는 `unclassifiedRevenue`에 그대로 옮기고 두 새 수입은0; 기존 `lostSales`는 코드상 오판매 이탈로 좁혀져 있지만 배포 이력 전체를 보장하지 않으므로 보수적으로 `unknown`에 옮긴다. 연구 대기/비현금 재료는0으로 시작. `supplierUnlocked`는 과거 날 납품도 참이므로 혼합매출에서120G를 무조건 빼지 않는다. UI는 “이전 저장의 미분류 수입/미분류 미구매”로 표시하고 새 사건부터 정확히 분류한다. 총돈·재고는 이행으로 변경하지 않는다. v3의 금액은0 이상 기존 매출 상한 내, 각 이유/연구대기 수는0..3, 합계 미구매+연구대기+served<=customer로 검증한다. 구버전에서 기록되지 않은 과거 거절까지 복원하지 않는다. 직렬화한 호환 합계와 세부합계가 다르면 손상 저장으로 처리한다. Game이 담긴 도입부·일반영업 저장 모두 같은 디코더를 사용한다.

**검증 계약.** day3 숙면2+시야1=108G, 협회1회=120G, 합계수입228G를 동시에 확인. 재료구매12G·투자90G가 있으면 현금변동126G(지원/기타 현금0 가정). 첫 오제안0건→두 번째 오제안1건; 품절 확인→보충→성공은0건; 품절 확인→보류확정은1건; 미발견 요청은 연구 대기; 창 반복 열기·저장 복원·납품 두 번째 호출은 추가0. 과거 저장의 합계/돈/재고 보존, 다음날 일일 초기화 검증.

## 실행 순서와 승인 경계

1. **현재 실행:** 확인된 F08/F09를 수정한다. F01–F07·F10은 설계만 채택하고 새 고객/메모/예약/원장 시스템을 함께 구현하지 않는다. 실제 버그 코드·테스트 실행 여부는 별도 담당 기록을 따른다.
2. **콘텐츠·텍스트 후속:** SR01 메모, SR06 경계 안내, SR07 이미 있는 원가의 설명 보강을 검토한다. 모두 이번 실행에서는 설계만 진행했다.
3. **독립 소규모 기능 승인 후:** SR02 연구 노트, SR03 순수 수요 조회, SR04 단일종 직접 버튼을 각각 별도 작업으로 검증한다.
4. **상태 확장 승인 후:** SR08 일일 분류 상태와 마이그레이션을 구현하고, SR05 고객ID·약속 이벤트·이관 및 대사를 연결한다. 미래 상세 거래 로그는 합계만으로 부족한 사용 목적이 확인될 때 착수한다. 고정표를 읽는 SR03은 SR08 구현 없이도 가능하지만 실제 놓친 수요 기반 예측은 SR08 이후다.
5. **후속 콘텐츠/경제:** 새 희귀 연구·예약·수요 확대는 별도 플레이테스트와 승인 이후. F11–F14 아트·레이아웃·발명 연출·재고 시각화는 낮은 우선순위로 보류한다. F10 기능 정산은 F14 마감창 외형 작업을 기다리지 않는다.

콘텐츠 문서와 CR04 단일종 조건, CR05 지급 시점·후보 수량을 맞췄고 구세이브 정책과 SR08 이유 분류를 위와 같이 제안했다. 모두 후속 구현 승인 시 함께 검토할 계약이다. 신규 기능의 수용 기준은 향후 테스트 요구이며, 이 문서가 이미 실행되어 통과한 테스트 결과라는 뜻이 아니다.
